## A 组 · 影响数据模型或 API 契约

### Q-01 功能面边界 → 接受裁剪

**结论**：不追加任何被裁掉的功能。

**执行方式**：**功能面裁剪，工程完成度对标生产系统**。不追求功能数量对齐 Waline，
但迁移体系、Docker、测试、日志、文档、错误处理这些工程标准一样不降。

**因此明确不做**：数据迁移导入、图片上传、点赞/表情反应、页面浏览量、置顶、私密评论、
编辑撤回、实时推送、多语言 i18n。

---

### Q-02 评论者邮箱是否必填 → 必填，站点不可关

**设计影响**：
- 新增决策 **D18**。站点配置里不再有 `requireEmail` 开关。
- 声誉机制与回复通知对**每一条**评论都成立，审核语义没有例外分支。
- API 校验层把邮箱作为硬性必填字段，缺失返回校验错误而非降级处理。

---

### Q-03 邮箱声誉作用域 → 站点级

**设计影响**：
- `members.review_required` / `spam_count` 按 `(site_id, email)` 维度存储，与整体数据隔离模型一致。
- 跨站垃圾发送者需要在各站点分别标记。若将来真被跨站刷，可再加「提升为实例级」的路径。

---

### Q-04 删除顶层评论 → 不级联

**设计影响**：
- 删除顶层评论时，子回复**保留**，父评论位置在列表中渲染为「该评论已删除」占位。
- 评论表已有软删状态（`status = 'deleted'`），无需额外结构。
- **明确避开 Waline 的行为**：Waline 会静默级联删除整棵子树且不提示影响范围。

---

### Q-05 评论排序 → 只要 latest / oldest

**设计影响**：
- `GET /api/v1/comments` 的 `sort` 参数只有两个枚举值。
- 无需在评论或线程表上维护任何热度分字段。

---

### Q-06 管理台角色模型 → IdP 角色命名约定驱动 ⭐

**你的结论**：
- `<前缀>.OWNER` = 全实例管理员
- `<前缀>.ADMIN.<站点 ID>` = 站点管理员

**设计影响（一次实质性升级：站点级权限从 P2 提到 P0）**：
- 新增决策 **D15**。**本系统不存储任何角色授予关系**，没有 `admin_site_grants` 之类的授权表。
- `admins` 表**刻意不存 `role` 字段**，只记录「谁登录过」用于审计关联。
- 角色前缀做成环境变量（同一 IdP 中区分多个部署/环境）。
- claim 路径做成可配置，默认读 `roles`，兼容 `groups` 与 Keycloak 的嵌套结构（`realm_access.roles`）。
- **撤销语义**：会话内缓存权限快照 + 较短的重校验周期；高权限操作强制回查。
  否则在 IdP 侧撤销角色后权限无法及时失效。

---

### Q-07 服务端到服务端写入 → 需要，走外部 OIDC ⭐

**设计影响（比原方案更简洁）**：
- 新增决策 **D16**。**不需要自建 Admin API Token 表**，也不需要 Token 管理界面。
- 脚本 / CI 通过同一 IdP 的 **client credentials** 流程取得 access token，
  以 `Authorization: Bearer` 调用管理 API。
- 需要实现：JWKS 校验、`aud`（受众）校验，以及 client credentials 客户端的配置文档。

## B 组 · 需要提供的信息

### Q-08 OIDC 提供商 → ZITADEL

**设计影响**：
- 新增决策 **D14**：**ZITADEL 为参考实现**，但客户端按**标准 OIDC** 实现，
  只依赖 discovery + JWKS + 标准 claims，不硬编码厂商特性 → 保留对其他 Provider 的支持。
- 交付物需包含面向 ZITADEL 的接入指南（应用创建、client credentials 客户端、
  角色定义与授予、回调地址白名单）。
- 集成测试可针对 ZITADEL 的容器镜像运行。

---

### Q-09 渲染与高亮技术栈 → Unified.js + Shiki + MathJax

**你的结论**：Markdown 采用 Unified.js 渲染处理，通过 Shiki 进行代码高亮，MathJax 进行公式渲染。

**设计影响**：
- 新增决策 **D19**。技术选型表全面替换：~~markdown-it~~ → **Unified.js**；
  ~~KaTeX~~ → **MathJax**；~~highlight.js 备选~~ → **Shiki**。
- XSS 消毒位置升级：改用 **`rehype-sanitize` 在 rehype AST 层消毒**，
  比原先设想的字符串级消毒（DOMPurify / sanitize-html）更可靠，且天然贴合 Unified 管线。
- Shiki 语言包需按需加载，否则构建产物会明显膨胀。

---

### Q-10 邮件发信 → 标准 SMTP 接口，站点级配置 ⭐

**设计影响**：
- **SMTP 配置从实例级改为站点级**：每个站点在后台填自己的 `host` / `port` / `secure` /
  `user` / `pass` / 发件人信息。
- 配置落在 `sites.settings.smtp`，**密码需加密存储**，读接口只回显「是否已配置」。
- 新增风险项：加密密钥丢失则需重新填写 SMTP 密码。
- outbox 投递需按站点取对应 SMTP 配置，因此 worker 要按站点分组处理。

---

### Q-11 反垃圾兜底 → 不预留

**设计影响**：
- 站点配置里**不设**人机验证相关字段，数据模型也不留钩子。
- 主文档风险表如实记录：被刷时需要改造数据模型与站点配置。
- 当前防线仅剩：站点级频率限制、蜜罐字段、邮箱声誉降级、人工批量审核。

---

## C 组 · 需要拍板的默认值

### Q-12 无来源头请求 → 站点级开关 ⭐

**你的结论**：不需要认证的 API 留**站点级开关**决定是直接 403 还是直接放行；
需要认证的 API 不检查来源头。

**设计影响（鉴权模型被明确切分为两类）**：

| 端点类别 | 鉴权 | 来源头校验 |
| --- | --- | --- |
| 公开端点 | `X-Recado-Site: <site key>` | 按站点级 `originPolicy`：`strict` → 403，`lenient` → 放行但限流更严 |
| 管理端点 | 会话 Cookie 或 OIDC Bearer token | **完全不检查** |

- 站点配置新增 `originPolicy`（默认 `strict`）。
- 后台需提供「来源校验自检」工具（已列入风险对策）。

---

### Q-13 管理台技术与语言 → Tailwind + shadcn/ui，中文

**设计影响**：一期不引入 i18n 框架；文案集中管理但不做多语言切换。

---

### Q-14 项目名 → `recado`

**设计影响**：npm 包名 `@recado/client`、镜像名 `recado/recado`、数据库名 `recado`、
环境变量前缀 `RECADO_`。

---

### Q-15 规模预期 → 小规模 ⭐

**你的结论**：1–3 个站点，单站 < 1000 条评论。

**设计影响（原性能目标属于过度设计，已下调）**：
- 压测目标从「单实例 10 万评论 / 1000 篇 / 50 QPS」下调为
  **「3 站点 / 3 万评论 / 300 篇文章 / 20 QPS」**，仍留约 10 倍余量。
- 索引策略**不因规模小而省略**——索引是设计正确性的一部分，不是规模优化。
- 管理台关键词检索从 `tsvector` 全文索引**降级为 `ILIKE`**（1000 条评论下完全够用），
  `tsvector` 移到 P1。这能省掉一期的一块工作量。

---

### Q-16 站点标识 → 一律 UUID ⭐

**你的结论**：不要提供站点 slug 配置功能，所有标识站点的地方都用 UUID，
Display Name 仅在后台展示用。

**设计影响**：
- `sites` 表**移除 `slug` 字段**；`name` 降级为纯展示字段，不参与任何标识、URL 或授权。
- OIDC 角色名中的站点部分使用 UUID：`<前缀>.ADMIN.<站点 UUID>`。
- 后台路由以 UUID 标识站点。
- 好处：站点改名（哪怕很频繁）完全不影响 IdP 侧的授权配置。

---

### Q-17 无角色用户 → 拒绝登录

**设计影响**：
- `ADMIN_BOOTSTRAP_EMAILS` 之类的环境变量兜底**不做**。
- 无匹配角色 → 拒绝登录、**不产生会话**、返回「无权限」提示。
- **新增风险**：首次部署时若 IdP 侧角色未配好会把自己锁在门外。
  对策：部署文档把「先在 IdP 创建 `PREFIX.OWNER` 角色并授予自己」列为第一步前置条件，
  并提供 CLI 诊断命令打印本次登录解析到的角色与可用站点列表。

---

### Q-18 机器调用的角色约定 → 复用同一约定

**设计影响**：
- 机器主体与人类主体使用**完全相同**的角色命名约定。
- `admins.kind`（`human` / `machine`）仅供展示与审计，**不参与授权判定**。
- 机器主体同样在 `admins` 表落一条记录，供审计日志关联。
